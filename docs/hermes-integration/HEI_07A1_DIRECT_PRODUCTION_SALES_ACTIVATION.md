1. Acceder a `https://blackpenguin.ai/admin/ai-settings`, pestaña **Sales Agent**. No hay selector en Company Onboarding o Project Onboarding. Revisar que LangGraph sigue seleccionado y que Hermes indica `Private SDK ready`.

Publicar no cambia el motor. No cambiar el prompt para probar el transporte. Regresar a Sales Agent y refrescar estado. El control permite seleccionar Hermes cuando la política publicada es válida y el SDK está disponible.
3. IMPORTANTE: el switch es GLOBAL para nuevos eventos comerciales elegibles en todas las compañías y proyectos. El nuevo código no implementa un canary por lead. Coordinar una ventana controlada sin tráfico real no previsto; si no se puede controlar el tráfico, no seleccionar Hermes todavía. Registrar el cambio con la nota del superadministrador y confirmar. No se requiere redeploy ni editar DB.
4. Registrar manualmente un lead usando un número propio autorizado, consentimiento, proyecto activo/aprobado y configuración Telnyx real SMS o WhatsApp ya operativa. No requiere `is_test`, un ID en GitHub ni caducidad especial. No utilizar proyectos o leads marcados `is_demo` para el canal live. El primer contacto sigue perteneciendo al mecanismo habitual de BlackPenguin y respeta el canal, templates y ventanas operativas. Responder desde el teléfono. El webhook normal debe generar el job, el worker fijar Hermes y el SDK preparar el turno. Verificar respuesta en teléfono y Conversation Inspector (motor, estado, propiedad y recibos). Un saludo inicial por sí solo no demuestra que Hermes haya ejecutado un turno.
5. Probar SMS y WhatsApp por separado; continuidad de propiedad, opciones ordinales, cambio de preferencias, búsqueda temporal, no-match, planos/brochure/galería, citas confirmadas explícitamente, reprogramación, cancelación y seguimientos. Usar catálogo real verificado, un calendario de pruebas o un slot autorizado y no interferir con compradores. Confirmar efectos reales en Telnyx/Calendar y ausencia de duplicados. No considerar un resultado verde en CI como evidencia del proveedor real.
6. Si hay fallos, volver explícitamente a LangGraph en Sales Agent, confirmar y comprobar nuevos eventos. Eventos previamente fijados conservan el motor/política: no se reproducen por el otro motor. Trabajos Hermes que no puedan finalizar quedan en revisión/reconciliación; no reenviar a ciegas mensajes o citas. El rollback administrativo no cancela operaciones ya realizadas ni garantiza migración de todo contexto específico del motor.

## Contratos conservados

- El selector persistente `active_sales_engine` sigue siendo la autoridad para nuevos eventos. El SDK no puede recibir prompts o IDs de alcance arbitrarios: recibe job/run autenticados y verifica inbound, oportunidad, pin, versión, mensaje, destino y reserva. La vinculación de alcance por ejecución permanece, pero se obtiene de la BD, sin allowlist manual. `require_scoped_entities`, consentimiento/opt-out, verificación de sender, aprobación de proyecto, pausa y validación de efectos siguen en los handlers existentes. No se bloquea STOP por consentimiento antes del handler de opt-out.
- Los eventos fijados anteriormente no cambian de motor. No existe fallback automático. La indisponibilidad de Hermes debe generar revisión, no duplicar acciones con LangGraph.
- El SDK privado no recibe las credenciales de Telnyx ni Calendar; el dispatcher y las operaciones existentes son dueños de efectos reales. Se reutiliza la BD productiva y no se agregan migraciones. Todavía no hay una identidad DB de privilegio mínimo ni firewall de egress por destino. La disponibilidad del SDK no demuestra saldo, validez efectiva de la API key, calidad de respuestas o entrega real.
- Company/Project Onboarding y su worker conservan los servicios existentes. `runtime_connected_to_live` ahora refleja selector, publicación habilitada y readiness, no aceptación de proveedores.
- En esta versión el deploy requiere seleccionar LangGraph y verificar que no haya turnos Hermes en curso o con efectos pendientes antes de futuras actualizaciones. No cambiar el selector durante el deploy. Esta decisión evita reemplazar el runtime durante un turno; no es una exigencia para cambiar de motor o registrar leads durante el funcionamiento normal. No se implementó un bloqueo distribuido de mantenimiento ni drenaje automático de todos los trabajos.
