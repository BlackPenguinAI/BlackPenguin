## What changed

- `sales_agent/live_worker.py` supplies the explicit Hermes inbound callback to the dual-engine router. `engine_router.py` respects a handler's false result instead of marking a pending/review job as completed. The readiness gate is still hard false; no automatic fallback.
- `hermes_sales_core/live_job.py` coordinates the existing claim, deterministic STOP/handoff, reserve, remote preparation, provisional send, accepted receipt, existing CRM and native operation adapters, and final inbound completion. No SDK imports in the API process. Existing provider and Calendar services remain owners of external effects.
- `hermes_sales_core/sdk_service.py` defines a separate private FastAPI application, not mounted on the public API. The only route accepts job/run IDs (extra request fields forbidden); a separate >=32-character bearer secret, fixed internal origin, no redirects/proxy, bounded timeout, single SDK process lock, scoped event/policy validation and immutable draft replay. It uses the same pinned SDK already installed by `services/hermes_worker/Dockerfile`.
- `live_preparation.py` releases database transactions before inference, rolls back read-only tool transactions, and uses the current revision and job claim again before storing a draft. This does not enable the runtime for real traffic.
- `provider_delivery.py` creates immutable per-part plans from canonical channel formatting. Per-part SHA-256 and share IDs, never raw bearer URLs in the Hermes receipt. Verifies scope, consent, continuity epoch, pinned policy, current tool permissions, current approved project and action restrictions, booking snapshot or file bindings. Explicit authorization at both queue creation and immediately before the provider call. Exact persisted outbox/message correlation only.
- `sales_agent/live_service.py` reuses the existing renderer, monetary and language checks, outbox, provider routes, Telnyx calls, and webhook correlation. Hermes requires unchanged rendered content; supplemental delivery does not overwrite the provisional reply in `AgentRun`. Existing outbox under Hermes must be reconciled, never automatically resent. No engine impersonation. The existing non-Hermes branch remains in place.
- `production_tools.py` rechecks approval and excludes demo projects at native live operation authorization. `bp_state_store.py`, `bp_operation_receipts.py`, `conversation_parity.py`, and `bp_turn.py` recognize `read` as stronger accepted provider evidence.

## Transaction and recovery contract

1. Worker claim + scope/event pin -> reserve AgentRun and commit before contacting the private service.
2. SDK prepares draft only. Recheck claim, scope, epoch, published version, state revision and store immutable draft; then commit.
3. Provisional dispatch plan -> shared dispatcher -> exact accepted provider/outbox receipt -> commit Hermes state and AgentRun. `queued`/`sending`/`scheduled` with a real provider ID is pending, not a second send. Poll via the existing webhook-updated database state, every 30 seconds, up to 10 total job attempts. Unknown/failed/partial group -> staff review. No new model request for a persisted draft.
4. CRM preferences may update using the existing evidence-backed writer. Booking uses the existing scheduling service and durable Calendar operation, then sends the confirmation. It does not claim Calendar sync succeeded. Material batch uses the existing share service and approval bindings. Issue, hash plan and first queued outbox share the first dispatch transaction. Subsequent partial/ambiguous group -> review; never remint an access automatically. Completed accepted groups can be reconciled without calling the model or provider again.
5. Mark inbound handled only after all intended delivery receipts exist. Deterministic control paths do not create fake model runs. STOP changes consent and disables automation; human/security handoff uses existing governance. The current global selector stays closed.
